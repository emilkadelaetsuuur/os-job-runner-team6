1. Design in one diagram

The server listens on one TCP port. Workers connect to it (so only the server's port must be reachable) and announce K; the server keeps a free-slot count per worker. All job records live in one table in the server, protected by one mutex; the journal jobs.log and the per-job output files out/<id> live on the server's disk.

2. The protocol

One line per message, ending in \n, read through a buffer in a loop. Commands are escaped (\\, \n, \r) so they always fit in one line.

MessageFieldsSender → receiverAnswer
SUBMITtimeout, priority, commandclient → serverID T12-7
STATUSidclient → serverSTATE T12-7 DONE 0 (any of the six states)
CANCELidclient → serverCANCELLED T12-7 or FINISHED T12-7
FETCHidclient → serverOUTPUT <n> + n raw bytes, or NOTFINISHED T12-7
(any, bad id)—server → clientUNKNOWN <id>; malformed: ERROR <text>
HELLOKworker → servernone; first line of a worker connection
RUNid, timeout, commandserver → workerlater DONE
CANCELidserver → workerlater DONE … CANCELLED
DONEid, kind (EXIT/TIMEOUT/CANCELLED/SIGNAL), code, nworker → servernone; n raw output bytes follow; frees the slot
BYE—worker → servernone; sent after SIGTERM, after all DONEs

How the answer to fetch ends: it does not need an end marker. OUTPUT <n> is a length prefix; the client reads exactly n bytes with read_exact() and writes them unchanged, so output with many lines and no final newline arrives byte for byte.

3. The policy and a trace that proves it

Priority with aging. The next job is the QUEUED one with the highest effective priority min(9, priority + seconds_waited / AGING), ties going to the older job; aging guarantees that a priority-0 job cannot starve behind a stream of higher-priority work.

Trace from tests/policy_trace.sh (real run, Ubuntu, one worker with K=1, AGING=1 s so the effect shows within seconds). T12-1 (sleep 4) keeps the worker busy while T12-2…6 queue up; T12-7…10 (priority 5) keep arriving every 2.5 s:

job T12-2 "echo starver" priority 0     job T12-5 "echo high"  priority 9
job T12-3 "echo low"     priority 0     job T12-6 "echo mid-b" priority 5
job T12-4 "echo mid-a"   priority 5     T12-7..10 "sleep 2; echo late-N" priority 5
dispatch T12-1 -> worker 1 (priority 0, effective 0, waited 0 ms)
dispatch T12-5 -> worker 1 (priority 9, effective 9, waited 3751 ms, 5 queued left)
dispatch T12-4 -> worker 1 (priority 5, effective 8, waited 3819 ms, 4 queued left)
dispatch T12-6 -> worker 1 (priority 5, effective 8, waited 3834 ms, 3 queued left)
dispatch T12-7 -> worker 1 (priority 5, effective 6, waited 1362 ms, 2 queued left)
dispatch T12-2 -> worker 1 (priority 0, effective 5, waited 5988 ms, 2 queued left)
dispatch T12-3 -> worker 1 (priority 0, effective 6, waited 6032 ms, 1 queued left)
dispatch T12-8 -> worker 1 (priority 5, effective 5, waited 989 ms, 0 queued left)

Priority 9 runs first; the two priority-5 jobs follow in submission order; T12-7 (priority 5, effective 6) still beats the priority-0 jobs. But by the time T12-7 finishes, the starver T12-2 has aged to effective 5 and wins the tie against the newer priority-5 job T12-8, which runs last: no starvation.

4. Part 2: the journal

Line format (jobs.log, written only with journal_append(), i.e. one write + fsync, under the table mutex):

SUBMIT T12-7 <timeout> <priority> <escaped command>
STATE T12-7 <QUEUED | RUNNING | DONE 0 | KILLED TIMEOUT | KILLED SIGNAL 9 | CANCELLED>

Write first, then answer. handle_submit() appends the SUBMIT line, then adds the job to the table, then sends the id. Every state change goes through job_set_state(), which appends the STATE line before changing the table. A job's output is written to out/<id> and fsync'ed before its final STATE line.

Restart, in order (recover(), before the first accept): (1) journal_open() cuts a torn last line; (2) every line is replayed with apply(), which only changes the table, never writes, and skips lines it does not understand; (3) every job still RUNNING gets a STATE … QUEUED line and waits for a worker; (4) the next id is the last SUBMIT plus one. Row 13, real run: the journal when the server was killed with kill -9, and the restart:

SUBMIT T12-1 10 0 echo a          server: listening on port 5000
STATE T12-1 RUNNING               server: state T12-2 RUNNING -> QUEUED
STATE T12-1 DONE 0                server: recovered 3 jobs from jobs.log (6 lines, 0 skipped):
SUBMIT T12-2 20 0 sleep 4                 2 queued, of them 1 were RUNNING; next id T12-4
STATE T12-2 RUNNING               server: dispatch T12-2 -> worker 1 ...
SUBMIT T12-3 10 0 echo c          server: state T12-2 RUNNING -> DONE 0 ... T12-3 ... DONE 0

A command that must not run twice: echo 100 >> balance.txt. If the server dies while it is RUNNING, the first run may already have appended its line; after the restart the job runs again from the start and appends a second one. The same holds for anything with a side effect outside its own output: sending an e-mail, making a payment, mv of a file that the first run already moved.
