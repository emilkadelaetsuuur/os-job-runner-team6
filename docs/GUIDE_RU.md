# Как это устроено и что отвечать на защите

## Запуск на Ubuntu

```
make
./server 5000 &
./worker 127.0.0.1 5000 1 &
./client 127.0.0.1 5000 submit "echo hello" 10      # -> T12-1
./client 127.0.0.1 5000 status T12-1                # -> T12-1 DONE 0
./client 127.0.0.1 5000 fetch T12-1                 # -> hello
./tests/selfcheck.sh                                # все 13 проверок
./tests/policy_trace.sh                             # трасса политики для отчёта
```

## Демо на ярмарке (1–2 минуты, онлайн, камеры включены у ВСЕХ)

Две машины: два ноутбука в одной сети **или** две виртуалки (bridged) на
одном ноутбуке. На каждой показать `ip a`. Сервер и worker на одной машине = 0.

1. Машина 1: `./server 5000`. Машина 2: `./worker <IP машины 1> 5000 1`.
2. `./client <IP> 5000 submit "echo hello" 10`, потом `status`, потом `fetch`.
3. `./client <IP> 5000 submit "sleep 20" 30`, пока бежит: `kill -9 <pid сервера>`,
   на машине 2 `kill -TERM <pid worker>`. Снова `./server 5000`, снова worker.
   `status` старых задач — всё на месте, sleep перезапущен и дойдёт до DONE 0.

Перед слотом: машины запущены, загруженный коммит собран (`git log -1`).

## Что где

- `src/common.c` — `read_line()` (буфер, читает до `\n` в цикле: один write
  не равен одному read), `read_exact()`, `write_all()`, TCP, экранирование.
- `src/client.c` — формирует запрос, печатает одну строку, коды выхода 0/1/2/3.
- `src/server.c` — поток на каждое соединение; таблица `jobs[]` под одним
  mutex; очередь; `policy_next()`; `dispatch()`; журнал и восстановление.
- `src/worker.c` — один `poll()`-цикл; `run_job()` — единственный `fork()`.
- `src/journal.h` — выданный файл, не менять.

## Ответы на вопросы из задания

**Durability: «Покажите строку, которая пишется ДО ответа»** (будут спрашивать точно)
`server.c:363` в `handle_submit()`: `journal_append(journal_fd, line)` строки
`SUBMIT T12-7 …`, и только после неё `apply_submit()` и `send_line(fd, "ID …")`.
Для всех смен состояния — `job_set_state()` (`server.c:249`): строка
`STATE T12-7 DONE 0` пишется в журнал (`server.c:260`), потом `apply_state()`.
Вывод задачи пишется в `out/T12-7` с `fsync` (`save_output()`, `server.c:505`)
до того, как задача записана в журнал как завершённая.

**«Что происходит при перезапуске?»** `recover()`, `server.c:639`, по порядку:
1. `journal_open()` — открыть на дозапись, отрезать оборванную последнюю строку;
2. `journal_read_open()` + `journal_next()` — каждую строку отдать в `apply()`
   (`server.c:218`). `apply` только меняет таблицу и **никогда не пишет** в журнал,
   иначе при повторе каждая строка записалась бы второй раз. Непонятная строка
   пропускается;
3. все задачи в RUNNING → `job_set_state(QUEUED)` (новая строка в журнале):
   их worker умер вместе со старым сервером, запускаем с начала;
4. следующий id = последний SUBMIT + 1, id никогда не выдаётся дважды;
5. только после этого сервер принимает соединения.

**«Зачем fsync? kill -9 и выключение питания»** `write` отдаёт байты ОС, она
держит их в памяти и пишет на диск, когда захочет. `kill -9` убивает только
сервер, не ОС — байты, уже отданные ОС, всё равно попадут на диск. При
выключении питания умирает и ОС, и спасает только `fsync`, который ждёт,
пока байты реально на диске. `journal_append()` вызывает его после каждой строки.

**«Почему под mutex?»** Сервер многопоточный: строка журнала пишется и
применяется под одним `lock`, чтобы порядок строк в файле был порядком изменений.

**«Какую команду нельзя запускать дважды?»** Задача, бывшая RUNNING при падении,
выполнится ещё раз с начала. Для `echo` это безвредно, а для, например,
`echo 100 >> balance.txt` (или перевода денег, отправки письма) — нет:
первый запуск мог успеть дописать строку, второй допишет её снова.

**Protocol: «Клиент умер на середине submit. Где это обрабатывается?»**
`read_line()` в `common.c:54`: `reader_fill()` вернул 0 (EOF), неполная строка
выбрасывается, `serve_client()` выходит, поток закрывает сокет. Задача не
создаётся: `SUBMIT` обрабатывается только целой строкой.

**Scheduler: «Что голодает при priority и что это останавливает?»**
Без старения задачи с приоритетом 0 ждали бы вечно, пока приходят задачи 5–9.
`effective_priority()` (`server.c:271`): `priority + ожидание/AGING`, максимум 9,
при равенстве — более старая задача. Доказательство — `tests/policy_trace.sh`:
задача с приоритетом 0 обходит более новую задачу с приоритетом 5.
FIFO включается так: `POLICY=fifo ./server 5000`.

**Worker: «Какая строка превращает убийство по таймауту в KILLED, а не DONE 0?»**
`worker.c:412`: по дедлайну `kill_job(&slots[i], WHY_TIMEOUT)` запоминает причину
в `s->why` и убивает всю группу (`kill(-pid, SIGKILL)`). Потом `finish_job()`
(`worker.c:185`) смотрит сначала на `s->why`, а не на статус `waitpid`, и шлёт
`DONE <id> TIMEOUT`. У каждой задачи своя группа процессов (`setpgid` в ребёнке
и в родителе), поэтому `sh -c "sleep 100"` умирает вместе со `sleep`.

**«Отменяю запущенную задачу. Кто это замечает и как?»**
1. Клиент шлёт `CANCEL`; поток сервера пишет `STATE … CANCELLED` в журнал
   и шлёт worker'у `CANCEL <id>` (`handle_cancel`, `server.c:393`).
2. Worker: `kill_job(s, WHY_CANCEL)` (`worker.c:304`) → SIGKILL группе.
3. Ядро шлёт worker'у SIGCHLD; обработчик пишет байт в self-pipe, `poll()`
   просыпается, `reap_children()` делает `waitpid(-1, WNOHANG)`.
4. Worker шлёт `DONE <id> CANCELLED`; только тогда сервер освобождает слот.

**«Worker отключился»** — `serve_worker()` (`server.c:563`): его RUNNING-задачи
возвращаются в очередь.

**Testing: «Тест на отсутствие утечки дескрипторов»** — `selfcheck.sh`, строка 11:
`/proc/<pid>/fd` у сервера и worker до и после 100 задач. Все fd `O_CLOEXEC`,
концы pipe закрываются, сокеты закрываются в `conn_thread()`.

## Зомби и SIGTERM

- Зомби: SIGCHLD → self-pipe → `reap_children()` с `waitpid(-1, &st, WNOHANG)`.
- Сервер на SIGTERM печатает строку, закрывает порт, выходит. `SO_REUSEADDR`
  и повтор `bind` до 3 с: новый сервер стартует без `Address already in use`.
- Worker на SIGTERM: `shutdown_worker()` убивает задачи, ждёт их, шлёт
  `DONE … SIGNAL 9` и `BYE`, выходит. Сервер недоступен — всё равно выходит.
